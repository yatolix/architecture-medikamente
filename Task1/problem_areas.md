# Проблемные зоны в безопасности данных

На основании анализа текущей архитектуры и потоков данных компании Медикамента можно выделить следующие проблемные зоны по части обеспечения безопасности данных:

1. Нет ясности по срокам хранения и уничтожения данных
   Нарушен принцип минимальной необходмости из-за накопления избыточных данных, которые возможно не архивируется и безопасно не удаляются. Также повашается ущерб в случае утечки, т.к. утекут в том числе старые данные, которые давно должны были удалены. Кроме того, неясно назначение данных, которые собираются в расширенной форме заполняемой пациентами, например место работы/учёбы. Видится, что подобные данные избыточны, особенно когда доступ к этим данным никак не ограничен.
2. Отсутствие ролевого доступа при работе с данными
   Все кто имеет доступ к сетевым хранилищам, может просматривать и редактировать документы, что недопустимо. Если хотя бы одна учётная запись сотрудника будет скомпометирована, это можеет привести к массовой утечке данных, как медицинских так и финансовых.
3. Возможные неточности из-за коллизий в данных
   У сотрудников может быть открыта неактуальная версия раписания или журнала записей пациентов из-за чего могут возникать "двойные записи" к одному специалисту на одно и то же время. Это может приводить в конфликтным ситуациям и недовольству клиентов.
4. Отсутствует контроль целостности документов
   Проблема в том, что заключения врачей или анализы могут быть изменены задним числом, сфальсифицированы после "подписания" врачом. Это может нести прямую угрозу жизни пациентам из-за некорректности данных.
   Необходима юридическая фиксация документов в хранилище.
5. Файлы с медицинскими изображениями хранятся без должного контроля
   Проблема в том что файлы-изображения (МРТ, Рентген) хранятся в общем реестре с анализами. Доступ к ним никак отдельно не контролируется. Отсутствует аудит.
   Возможны несанкционированный доступ и утечка, что является прямым нарушением "врачебной тайны".

# Защита данных

Ниже перечислены категории данных, которые подлежат защите (с примерами) и сформулированы способы их защиты в зависимости от того находятся ли данные на хранении или в стадии передачи, или отображаются в пользовательских интерфейсах.

## Способы защиты по категориям

### Персональные данные

**Например**: ФИО, паспорт, адрес, контактные данные, полис.

**При хранении**: Шифровать на уровне БД дабы минимизировать риски даже если злоумышленники получат доступ к БД. А для аналитики или на тестовых средах данные необходимо обезличить.

**При передаче**: Обязательное шифрование канала (TLS 1.3). А при передаче между системами использовать токенизацию.

**При отображении**: Обфускация и маскировка в интерфейсе. Если нужен полный доступ, то только по требованию на ограниченное время.

### Данные представляющие медицинскую тайну

**Например**: Диагнозы, назначения, результаты осмотра, операции.

**При хранении**: Шифровать на уровне БД дабы минимизировать риски даже если злоумышленники получат доступ к БД. Заключения врачей хранить отдельно и использовать Электронные Подписи.

**При передаче**: Обязательное шифрование канала (TLS 1.3). Если врачи хотят обмениваться файлами, то только по защищённым каналам (не email). Например, можно поднять защищённый корпоративный мессенджер.

**При отображении**: Маскирование, но с возможностью динамически применяться в зависимости от роли. Например, врач видит все данные, а ассистент или медсестра - только ограниченный набор, остальное - замаскировано.

### Биометрические данные и изображения

**Например**: Фото, рентген, МРТ, УЗИ и т.п.

**При хранении**: Шифрование файлового хранилища.

**При передаче**: Обязательное шифрование канала (TLS 1.3).

**При отображении**: Неавторизованный персонал не должен видеть даже предосмотр файлов. А для пациентов можно использовать водяные знаки на изображениях.

### Финансовые данные

**Например**: реквизиты счетов, история платежей, реквизиты карт (если есть)

**При хранении**: Шифровать данные о транзакциях. Номера карт НЕ ХРАНИТЬ - использовать только токены, выданные платёжным шлюзом.

**При передаче**: В качестве платёжного шлюза использовать только PCI DSS сертифицированное решение. Внутрення передача - только токены по TLS.

**При отображении**: Для карт и счетов полное маскирование - максимум отображение последних 4 цифр для верификации сотрудниками в случае необходимости. Например, оператор может подтвердить клиенту по телефону что последний платёж осуществлялся по карте чей номер оканчивается на 1234.

### Метаданные, справочники и служебные данные

**Например**: расписания, логи, IP-адреса и пр.

**При хранении**: Если где-то встречаются PII (например в логах), то шифровать их.

**При передаче**: API ключи и сертификаты хранить с помощью секрет-менеджеров например тот же Hashicorp Vault.

**При отображении**: Строго применять ролевой доступ. Максирование или обфускация как правило не требуются. Главное чтобы сотрудники не получили больше информации чем им требуется для выполнения своих непосредственных обязанностей.

## Механизм тегирования

### Классификация тегов

* **По уровню конфиденциальности**: public, internal, confidential, restricted, critical.
* **По категориям данных**: pii, medical, financial, biometric, metadata
* **По согласиям на обработку**: agreement_given, agreement_revoked

### Особенности реализации

Для новых данных реализовать пометки в момент ввода данных в систему. Например администратор, который вводит данные, выбирает уровни конфиденциальности из выпадающего списка.

Для существующих данные можно применить автоматизированные инструменты, которые по шаблонам находят определённые атрибуты (например, номера паспортов) и найденным данным присваиваются соответствующие теги.

Для структрированных данных, хранящихся в БД, теги можно хранить в отдельных таблицах как метаданные, чтобы не смешивать их с основными бизнесовыми данными.

Для файлов можно использовать возможности файловой системы (атрибуты). Либо создавать отдельный реестр со списком файлов.

Внедрить использование тегов в политики доступа. Например, если запись помечена тегом restricted, то доступ к записи разрешён только ограниченному перечню ролей.

## Инструменты, способы и меры обеспечения конфиденциальности данных

### Шифрование

Т.к. текущие спосоы хранения (в общих папках) не дают возможность должным образом защитть данные, то подразумевается что структурированные данные переедут в БД PostgreSQL - там можно прикрутить инструменты Transparent Data Encryption.

Для шифрования "в движении" использовать TLS (HTTPS) а для передачи данных между сегментами сети можно поднять VPN  с помощью Wireguard.

Собственно сама по себе сегментация сети - тоже отдельная мира, которую можно к примеру реализовать с помощью Vmware NSX.

### Уровень приложений

Для начала, на уровне БД можно максировать данные путём создания VIEW, в которых будут замаскированы определённые поля прямо в SELECT операторе. Затем, можно выбрать подходящее расширение БД PostgreSQL которое позволит управлять маскированием более точечно.

Для аудита и мониторинга можно прикрутить SIEM системы, например начать можно с open source решений вроде WAZUH.
